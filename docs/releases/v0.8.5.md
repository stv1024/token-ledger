# TokenLedger v0.8.5

Released 2026-11-18. Shows the cache hit rate in the session summary and the
overview totals, and shows an upper bound of the rate when the cache-write
count is missing.

## Compatibility

Requires **Paseo >=0.11.0** on both the daemon and app, as in v0.8.4. Existing
`ledger.jsonl` records and `pricing.json` files are kept and are not rewritten.
The rate is calculated when the ledger is read, so earlier turns get it too.

## Changes

- **Hit rate in summaries.** The panel's session summary and the overview
  totals show the cache hit rate: cache reads divided by the complete prompt
  (uncached input + cache read + cache write).
- **Upper bound when the cache write is missing.** Paseo 0.16.1 does not report
  Claude or OMP cache writes, so their prompts are not complete. A missing
  write is unknown, not zero. But uncached input + cache read is the smallest
  prompt possible, so read / (input + read) is the highest
  rate possible. These turns now show that value with `≤`, for example `≤97%`,
  instead of `?`. The value is rounded up, so it stays a true upper bound.
  Turns with a complete prompt, such as Codex turns, still show the real rate.
- **How the summary joins the two.** The summary keeps the complete prompts and
  the lower-bound prompts in separate fields. For display, it adds the reads
  and prompts of both. If any turn gives only a lower bound, the whole value is
  an upper bound and shows `≤`, because each missing write can only make the
  prompt larger. With no such turn, the value is the real rate, as before.
  Turns with neither (snapshots, missing counts) are left out and counted in
  the label as `N unknown`. With no usable turn, the value is `–`.

## Known limits

A Claude turn often has only a few uncached input tokens, and the unknown
write is most of the prompt. Its bound is then near `≤100%`. That is correct,
but it says little. Only a cache-write count from Paseo can make the rate
exact; see the [usage API requirements](../paseo-usage-api.md).
